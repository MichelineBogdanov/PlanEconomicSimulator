# AGENTS.md

## Назначение

Этот файл определяет правила разработки PlanEconomicSimulator. Продуктовые требования,
границы прототипа и критерии приёмки находятся в [SPEC.md](SPEC.md).
Перед изменениями прочитай относящиеся к задаче разделы спецификации и существующий код.
Прямые указания пользователя имеют приоритет. При согласованном изменении решения обновляй
спецификацию вместе с реализацией; не меняй основной игровой цикл или объём версии молча.
Визуальные решения находятся в [DESIGN.md](DESIGN.md), команды и CI — в
[docs/DEVELOPMENT.md](docs/DEVELOPMENT.md).
Демография, факторы исполнения и контрольные сценарии описаны в [docs/PLAN_FACTORS.md](docs/PLAN_FACTORS.md).

## Общение и стиль

- Отвечай на русском. Имена типов, методов, переменных, файлов кода и комментарии пиши на английском.
- Переходи к делу; пользователь — опытный Java-разработчик, базовые объяснения не нужны.
- Пиши чистый код с минимальными комментариями для неочевидных правил и инвариантов.
- При исправлении ошибки коротко укажи причину, изменение и результат проверки.
- Для необходимых разрешений объясняй, что сделает команда и зачем.
- Различай реализованное, проверенное и запланированное. Не выдавай отсутствие запуска тестов за успех.

## Требования и рабочие решения

SPEC.md различает требования пользователя и предложенные решения прототипа.
Следующие технические настройки служат исходной базой разработки;
не называй предложенные ограничения и порядок выпуска ранее утверждёнными пользователем.

- Unity 6.6 (6000.6.0f1), C#, Windows x64, одиночная локальная игра.
- UI Toolkit, UXML, USS; 2D-карта с городами-узлами и маршрутами.
- Игрок составляет количественный план по городам и товарам; исполнение автоматическое.
- Подготовленные ветви выбирает игрок при срабатывании условий. Самовольного переключения нет.
- Рабочее предложение для первого выпуска в Steam — бесплатная демоверсия на одну пятилетку,
  на русском и английском; формат выпуска ещё можно изменить.
- Карточка предприятия — представление объекта и его параметров, а не карточная игровая механика.
- Не добавляй сервер, Spring, PostgreSQL, мультиплеер, DOTS/ECS или сторонний DI-фреймворк
  без конкретной задачи, которая их требует.

## Архитектура

- `Simulation.Core`: экономика, план, события, армия и месячный шаг; без Unity, Steam,
  файловой системы, UI и системного времени.
- `Simulation.Application`: команды, валидация, прогнозирование, фазы игры; без Unity API.
- `Simulation.Persistence`: чтение каталогов, сохранения и журнал решений.
- `Game.Presentation`: Unity-сцены, карта, ввод и UI.
- `Game.Platform`: адаптер Steamworks.NET и локальная реализация платформенных сервисов.
- Используй отдельные assembly definitions и явные зависимости. UI вызывает команды
  приложения и получает снимки/проекции состояния; не изменяет сущности симуляции напрямую.
- Не помещай экономическую логику в `MonoBehaviour`, `Update`, корутины или обработчики UI.
- В доменной модели используй стабильные идентификаторы; ссылки на Unity-объекты не входят в сохранения.
- Ввод валидируется на границе приложения. Некорректные данные не должны частично изменять мир.

## Детерминизм и экономические инварианты

- Один шаг симуляции — один месяц. Пятилетка — 60 шагов; FPS не влияет на результат.
- Количества ресурсов храни в целочисленных минимальных единицах с документированным масштабом.
  Применяй явные правила округления и проверки переполнения; не используй `float` для баланса ресурсов.
- Зафиксируй порядок обработки объектов и распределения дефицита, включая разрешение равных приоритетов.
- Все случайные игровые решения проходят через собственный воспроизводимый генератор
  с сохраняемым состоянием. Не используй `UnityEngine.Random`, глобальный `Random`, часы
  или порядок обхода хеш-коллекций как источник результата симуляции.
- Прогноз использует изолированную копию мира. Он не меняет состояние партии и её генератор
  и не раскрывает ещё неизвестные случайные события.
- Соблюдай порядок месячного расчёта из SPEC.md; не допускай повторного расходования товара
  или мгновенного прохождения всей производственной цепочки за один месяц.
- Производство, доставка, потребление и запас — разные величины и разные поля отчёта.
- Запасы не уходят в минус. Недостаток ресурсов ограничивает действие и фиксируется как причина отклонения.
- Экономическая цена ветви состоит из реальных ресурсов, времени и мощностей; ветвь не создаёт их бесплатно.
- Предсказуемые возрастные переходы включай в прогноз; не маскируй их случайными событиями.
- Сохраняй когорты, очереди демографических последствий и остатки округления. Рождения,
  смерти, переселение и мобилизация не должны дублировать население, потребление или потери.
- Смертность и отъезд не стирают накопленный дефицит; благополучие оценивается отдельно от выполнения задания.
- Различай базовые и отложенные кейсы PLAN_FACTORS.md; не расширяй прототип всеми событиями каталога сразу.

## Unity и зависимости

- Точная версия редактора — `6000.6.0f1` (revision `f7f8ed4d1e24`), по прямому выбору пользователя.
  Источник версии — `ProjectSettings/ProjectVersion.txt`; не называй Unity 6.6 выпуском LTS.
  Не подставляй произвольную patch-версию и не обновляй редактор в рамках несвязанной задачи.
- Профиль API — .NET Standard 2.1; используй поддерживаемую закреплённым редактором версию C#.
  Не предполагай доступность API современных .NET SDK внутри Unity.
- Версии пакетов закрепляются в `Packages/manifest.json` и `Packages/packages-lock.json`.
- Исходники и содержимое Unity храни вместе с `.meta`. Сохраняй GUID при перемещении ассетов.
- Сцены и ассеты сериализуй в текстовом формате; включи Visible Meta Files.
- Не коммить `Library`, `Temp`, `Obj`, `Logs`, `UserSettings`, сборки и результаты тестов.
  Не редактируй генерируемые Unity `.csproj` и `.sln` как источник конфигурации проекта.
- Для первого локального прототипа используй Windows x64/Mono. IL2CPP — отдельная проверяемая
  настройка сборки при необходимости; Steam не требует перехода на IL2CPP.
- Все пользовательские строки проходят через Unity Localization. Диагностические коды стабильны,
  отображаемый текст локализован. Не используй переведённые названия как идентификаторы.

## Данные и сохранения

- Рецепты, мощности, нормы, сценарии и события — конфигурационные данные, не литералы в UI.
- Проверяй ссылки, единицы измерения, допустимые значения и совместимость каталогов при загрузке.
- Сохранение включает версию формата и каталога, весь воспроизводимый мир, план, решения,
  ветви, отчёты, строительство, поставки в пути и состояние генератора.
- Запись выполняется на границе месяца через временный файл и замену с резервной копией.
- Обновление опубликованного формата сопровождай миграцией и тестом на старое сохранение.
- Сохраняй Steam-профили раздельно. Локальный профиль разработки не смешивается со Steam-профилем.
- Облачная синхронизация охватывает сохранения, но не логи и настройки конкретного компьютера.

## Проверки и рабочий процесс

- Сначала проверь реальное состояние проекта и установленную версию Unity; наличие этого файла
  не означает, что Unity-проект или тестовые команды уже созданы.
- Для правил симуляции добавляй содержательные EditMode-тесты: балансы, ограничения,
  детерминизм, прогноз, ветвление, сохранения и кризисы. Используй Unity Test Framework/NUnit.
- PlayMode-тесты проверяют интеграцию, переходы экранов и взаимодействие UI с приложением.
- Не создавай тесты, которые просто повторяют реализацию, и не запускай полный набор
  повторно без изменения кода, ошибки или новой причины проверки.
- CLI-запуски Unity выполняй с `-batchmode`, `-runTests`, `-testPlatform`, путями XML-результатов
  и лога. Не добавляй `-quit` к запуску тестов: редактор может завершиться до окончания тестового прогона.
- Не запускай два редактора для одного каталога проекта. Не удаляй lock-файлы и не завершай
  пользовательский редактор для обхода блокировки.
- Проверяй код завершения, XML и ошибки компиляции в логе; пустой прогон не означает прохождение тестов.
- Проверки, зависящие от графики, выполняй с графическим устройством; `-nographics` не является
  универсальным параметром для UI/PlayMode-тестов.
- Команды сборки и тестов автоматизируй PowerShell-скриптами при создании Unity-проекта.
  До их появления не ссылайся на них как на существующие инструменты.
- При блокировке лицензией, отсутствием редактора или модулей укажи точную причину
  и уже выполненные независимые проверки.
- Не записывай учётные данные, лицензии, токены или Steam Guard-коды в репозиторий и логи.

## Steam

- Экономическое ядро и тесты не зависят от доступности Steam.
- Основная игра и Demo используют одну кодовую базу и отдельные профили сборки/App ID.
- Первый публичный объём, обещания магазина и реально выпущенные возможности должны совпадать.
- Публикация, оплата, работа с учётной записью и загрузка в публичную ветку не следуют
  автоматически из обычной задачи на изменение кода; учитывай явную авторизацию пользователя.
- Перед задачами выпуска сверяй актуальные требования с официальной документацией Steamworks.

## GitHub, review и доставка

- Репозиторий: https://github.com/MichelineBogdanov/PlanEconomicSimulator, владелец — MichelineBogdanov.
- Работай в коротких ветках `feat/…`, `fix/…`, `chore/…`, `docs/…` от актуального `main`.
  Одна ветка и PR — одна связная задача; отдельная постоянная `develop` не нужна.
- Перед отправкой проверь diff, `.meta`, отсутствие секретов, локальные проверки и описание изменений.
  Коммиты — короткий английский Conventional Commit; PR и отчёт — на русском.
- Изменения направляются через PR в `main`. Review и ручной squash merge выполняет пользователь.
  Не одобряй свои PR, не включай auto-merge, не сливай и не отправляй обычные изменения прямо в `main`.
- Для совершенно пустого репозитория допустим один начальный README-коммит для создания `main`;
  реализация, документация и workflow затем поступают отдельным PR.
- При работе через аккаунт владельца PR будет его собственным: GitHub не позволяет автору
  формально Approve свой PR. В этом режиме обязательны проверки и ручное слияние пользователем;
  требование одного approval включать после подключения отдельного автора PR/бота.
- Целевая защита `main`: PR, обязательный `CI gate`, актуальная ветка, разрешённые обсуждения,
  запрет force push и удаления. Файлы CODEOWNERS/workflow сами по себе не включают защиту на GitHub.
- GitHub Actions проверяет конфигурацию, EditMode и PlayMode на PR и `main`;
  после успешных проверок `main` собирает Windows-артефакт с SHA коммита.
- Workflow и зависимости Actions закрепляй на проверенные SHA. Доступ токена — минимальный.
  Не используй `pull_request_target` для запуска кода PR с секретами.
- Fork/Dependabot PR не получает Unity-секреты. Непроверенный Unity-код не проходит `CI gate`;
  для полного прогона владелец переносит проверенные изменения в доверенную ветку.
- Лицензия CI настраивается отдельно. Отсутствие лицензии/результатов/тестов — ошибка,
  а не успешный пустой прогон. Не выгружай учётные данные или локальную лицензию без отдельной задачи.
- Автоматическая доставка пока означает Windows-артефакт в Actions. Steam-публикация — отдельный
  процесс выпуска с явной авторизацией, без вымышленных App ID и аккаунтов.

## Графика и дизайн

- Используй DESIGN.md и docs/design/tokens.json; ретро-оформление не снижает читаемость данных.
- Экраны и карточки строятся компонентами UXML/USS, текст и числа не запекаются в изображения.
- Редактируемые оригиналы — ArtSource/, экспорт для игры — Assets/Game/Art/ вместе с `.meta`.
- SVG и текстовые UI-ассеты — обычный Git; тяжёлые исходники — Git LFS по `.gitattributes`.
- Для включаемых сторонних/генерируемых ресурсов заполняй реестр происхождения и лицензий.
- Визуальный PR сопровождай сравнимыми скриншотами и проверкой кириллицы, масштабирования и состояний.
